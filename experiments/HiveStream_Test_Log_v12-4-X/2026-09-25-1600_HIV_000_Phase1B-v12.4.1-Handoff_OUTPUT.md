# HiveStream — Project Status & Handoff (for GPT-5.6 Luna / cross-LLM continuity)

This doc is a snapshot for another LLM picking up this project cold. It assumes no prior context beyond what's written here. It supersedes prior handoff notes on Phase 1 status specifically; earlier architecture/priority decisions below are still current.

## 1. What HiveStream is

A browser-based P2P media distribution layer sitting on top of CyTube (cytu.be), a room-based video-sync platform. Core thesis: independently-sourced copies of the same content converge on the same P2P swarm so repeat viewers serve each other instead of hitting a central server.

**Stack:** Novage p2p-media-loader (P2P engine, pinned v4.0.0) + hls.js (playback, pinned v1.7.0) + WebRTC DataChannels (transport) + IndexedDB (persistence; OPFS deferred).

**Priority order (highest first):** P2P media distribution → persistent reuse → local ingestion → swarm discovery → playlist/media identity → seeding → server bandwidth reduction → playback synchronization (#8) → CyTube leader-behavior compatibility (#9, lowest, Phase 6 of 6).

**Repos:** `duckwerks/HiveStream` (canonical product repo) — README/PROJECT-STATE/ARCHITECTURE/ROADMAP/DECISIONS/OPEN-QUESTIONS/LLM-HANDOFF.md + src/tests/experiments/docs/archive. `calzoneman/sync` (CyTube's actual open-source server, useful for confirming client-side reverse-engineering against server truth). `duckwerks/cytube-knowledge` (older reverse-engineering reference notes, WS-0xx series).

**Evidence tiers used throughout:** SOURCE PROVEN / RUNTIME PROVEN / STRONG INFERENCE / UNPROVEN-OPEN / DESIGN PROPOSAL.

**Phase guardrail (still in force):** Project is at Phase 1 ("P2P proof," a standalone browser experiment). Do NOT modify CyTube or build local ingestion/replication until Phase 1's proof condition is met: **actual measured P2P segment bytes exchanged**, matching the intended controlled variant — not just peer connection.

## 2. Where Phase 1 stands as of the v12.4.1 session (2026-09-25)

The test harness is `experiments/HiveStream_Test_Log_v12-4-X/HiveStream_Phase_1B_Natural_Swarm_Diagnostic_v12-4-1.html`. It instruments hls.js + p2p-media-loader-hlsjs (v4.0.0) against RTCPeerConnection and exports a full JSON diagnostic per run. 68 JSON exports exist in that folder; deduplicating by `identity.runId`/`test.startedAt` (many filenames with "(1)/(2)" suffixes are incremental re-saves of one long-running session, not separate runs) gives **33 distinct test runs** across two laptops-worth of browsers (Chrome, Vivaldi) and a phone (Chrome, Vivaldi; wifi and 5G), in both `hybrid` and `p2ponly` transport modes.

### The finding: real P2P byte exchange happened once

One run — `HiveStream-Phase1B-v12.4.1-p2ponly-laptop-vivaldi-2026-09-24T234825408Z (2).json`, deviceLabel "laptop vivaldi," desktop Chrome 152, `transportMode: p2ponly`, `swarmMode: natural`, 15 minutes — got:

- **101,200,964 bytes p2pDown / 76,173,652 bytes p2pUp**, across a WebRTC data channel labeled `webtorrent`
- 4 distinct peer IDs seen via the swarm/tracker layer, but only **1 of the 33 runs had any `succeeded` ICE candidate pair at all** (38 succeeded-state records in this run; every other run — including some with up to 148 RTCPeerConnections — had zero)
- Discovery happened via `wss://tracker.openwebtorrent.com` only; the other two configured trackers (`tracker.novage.com.ua`, `tracker.webtorrent.dev`) returned zero peer activity in every run checked

### Why this still isn't Phase 1 proof

`verdict.proof` is false for this run because `verdict.p2pSegmentMatchedSelectedVariant` is false: **every segment transferred (28 HTTP-sourced + 36 P2P-sourced) came from manifest rendition index 0** (1280×720, infoHash `Dd+yrwrnofWI3vWhfz1l`), never from the intended locked "controlled" 480p rendition (index 3, 848×480, infoHash `i0q7IwL7towfhu4Xnofx`). `manifest.activeLevelIndex` was recorded as 3 (matching the intended lock) and `playerRecovery.levelDriftCorrections` was empty (no drift-correction logic ever fired) — yet the actual fetch URLs never touched the level-3 sub-playlist for the entire 15 minutes. **The `hlsInstance.currentLevel = found.index` lock in the MANIFEST_LOADED handler does not appear to actually constrain which rendition's segments get fetched.** This is the direct blocker to close before any future run can satisfy the strict proof condition — needs a hls.js-level investigation (is this a race between manifest-loaded-time locking and an ABR level guess already in flight? does p2p-media-loader's own stream selection override hls.js's currentLevel?).

### Who was the peer, actually? (important correction to an initial assumption)

Ed's working assumption was that the successful run was talking to his own phone (running the diagnostic concurrently) and/or a same-laptop Chrome instance that crashed mid-test. Cross-checking peer IDs against every run's own recorded `identity.actualP2PIdentity.peerId`:

- **One of the 4 peer IDs (`-PM0400-alSG3w9e09Ud`) is confirmed to be Ed's own phone** ("Phone Vivaldi 5g," which ran 23:55:45–23:57:59, inside the laptop run's 23:48:25–00:03:27 window) — but that peer's own event history shows only repeated `connect-error`s (`ICE connection disconnected`, `Data channel open timeout`) — **it never actually reached a connected state.**
- The two other peers with any connection attempt (`-8a7eNWCcnJoZ`, `-IEsruVyEBce3`) also show only `connect-error`s, never `connected`.
- **The one peer that actually opened the data channel and carried all 101MB/76MB (`-PM0400-6jnhDpApKDei`, mapped to `pc-12`/pcIndex 10) does not match any of Ed's own recorded peer identities across all 33 runs.** Its remote ICE candidates were a host mDNS candidate (`*.local`, not resolvable) plus two `srflx` candidates on public IP **146.70.230.118**. That IP falls in a /16 range (146.70.x.x) that a public IP-intelligence lookup shows is heavily used by **Mullvad VPN via M247 hosting (AS9009)** for VPN exit relays — strongly suggesting (not proven) this successful peer was an unrelated third party behind a VPN, not one of Ed's own devices. This connection opened within ~3 seconds of the laptop test starting, well before Ed's phone test began.

**Implication:** because `swarmMode` was `natural` (no custom swarm ID) against a very widely-used public HLS demo stream (`test-streams.mux.dev/x36xhzz`) on a public tracker, the swarm is not scoped to Ed's own devices — it's the same public infoHash anyone else running p2p-media-loader against that stream would join. The real P2P transfer likely happened with a stranger, not a controlled two-device test. **Before this can be called a real proof-of-concept, re-run with `swarmMode: "custom"` and a unique `swarmId`.**

### Instrumentation bug found in the diagnostic itself

The RTCPeerConnection-wrapper's icecandidate-**event** capture path (feeding `webrtc.peerConnections[].localCandidates`/`candidateTypes` and the top-level `network.candidateTypes` summary) is empty/zero across all 33 runs, including the successful one (0 local candidates recorded across 87 wrapped RTCPeerConnections in that run). The separate `getStats()`-**polling** path (`webrtc.candidatePairRecords`) is what actually surfaced real candidate-pair data, including the succeeded pair above. This likely explains why an earlier diagnostic session (v12.3) reported "0/17 runs, 100% null informative ICE data" — it was probably reading only the broken event-capture path. Recommend fixing or dropping the event-capture path in the next diagnostic revision in favor of the working getStats() path.

## 3. Test methodology / hardware context (for interpreting future exports)

- Laptop: HP Victus, i7, 32GB RAM, RTX 4060 8GB VRAM, 1TB NVMe SSD.
- Typical run pattern: 1–2 laptop browsers (Chrome + Vivaldi) started first as "super-seeders," left running until roughly half the ~10-min test video has played, then a phone test started to see if it behaves as a leech against the already-seeded laptop swarm.
- GitHub's 25MB upload cap plus browser memory limits (Chrome crashed at least once running concurrently with Vivaldi on the same laptop, losing that run's JSON) mean long runs are capped in practice — phone JSONs are kept under ~11MB deliberately.
- All test JSON + the HTML harness are mirrored to Google Drive in addition to GitHub.

## 4. Open items / recommended next steps

1. Re-run with `swarmMode: "custom"` + a unique `swarmId` to rule out public-swarm contamination and get a clean two-own-device test.
2. Diagnose why hls.js's segment-fetch URLs never honored the level-3 (controlled 480p) lock in the successful run, despite `LEVEL_SWITCHED` recording `activeLevelIndex: 3`.
3. Decide whether to keep or drop the (currently broken) icecandidate-event capture instrumentation now that `getStats()`-polling is confirmed to work on its own.
4. Investigate why only 1 of 3 configured trackers (`tracker.openwebtorrent.com`) ever returns peers.
5. Resolve tracker-hosting open questions for the eventual self-hosted WSS tracker: is a domain purchase strictly required for the target Always-Free tier, can it run on Ed's own laptop, is a TLS cert strictly necessary.
6. Reconcile HiveStream's architecture docs with the earlier-confirmed fact (WS-077) that CyTube's real production player is Video.js, not an independent HLS.js instance — the docs' assumed "Video.js → HLS.js → p2p-media-loader" chain doesn't match what exists in `calzoneman/sync` today.
7. Resolve the design tension between the rewatch-bandwidth thesis (wants cross-room swarm convergence) and room-scoped privacy (wants the opposite) before implementing the self-hosted tracker's `swarmId` scheme.
