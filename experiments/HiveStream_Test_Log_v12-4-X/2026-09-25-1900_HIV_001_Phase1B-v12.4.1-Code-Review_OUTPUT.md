## 1. Architecture overview

The file is a single self-contained HTML page with three structural pieces, in load order:

1. **`installPeerConnectionCapture()` IIFE (lines 20–454)** — runs before either media library loads. Monkey-patches `window.RTCPeerConnection` globally so every `RTCPeerConnection` the page (or any library on it) creates afterward is transparently wrapped and logged into a module-level array, exposed as `window.__HS_V11_PEER_CONNECTIONS`. This is a carryover from earlier versions (the `__HS_V11_*` globals date to the v11 revision per its own naming) — v12.4.1 still builds on it rather than replacing it.
2. **Library scripts** — `hls.js@1.7.0` (line 16, loaded *before* the capture IIFE) and `p2p-media-loader-hlsjs@4.0.0` (line 457, loaded *after* it, so it constructs its `RTCPeerConnection`s through the already-patched global).
3. **Main diagnostic script (lines 624–3634)** — an IIFE holding a large mutable state object `R` (the thing that eventually becomes the exported JSON), the UI panel/config wiring, the HLS.js + p2p-media-loader-hlsjs setup, and two independent ways of reading WebRTC connectivity back out of the capture layer (see §3.5/§3.6 — only one of the two actually works).

Two module-scope globals bridge pieces 1 and 3: `window.__HS_V11_PEER_CONNECTIONS` (array of raw, wrapped `RTCPeerConnection` objects — each carries its own diagnostic record on a `.__hsV11` property, *not* as a top-level property of the array element) and `window.__HS_V11_ACTIVE_RUN_ID` (a run-scoping guard).

## 3. How the pieces actually connect (notes beyond the map)

**3.1 — Constructor wrapping is sound.** `WrappedRTCPeerConnection` (350–449) builds a real native `pc` via `Function.prototype.bind.apply(Native, ...)`, attaches the diagnostic record via `makeRecord(pc)`, pushes `pc` (not the record) onto the module-scope `pcs` array, and returns `pc` explicitly — a standard, correct constructor-wrapping pattern. `pcs.push(pc)` (line 354) is the thing that makes `window.__HS_V11_PEER_CONNECTIONS` a **list of native pc objects**, each carrying its diagnostic record on `pc.__hsV11` — this distinction matters for §4.1.

**3.2 — Two independent state-rebuild sites for `R`.** The literal at 876–1074 and `resetRun()`'s rebuild at 2782–2948 are hand-maintained duplicates of the same ~150-key shape (confirmed by extracting every object key from both blocks and diffing — see §4.3). Every future field added to one needs a matching edit in the other or they silently diverge.

**3.3 — Run-scoping is handled carefully almost everywhere.** `attachHlsEvents()`'s `isCurrentRun()` (2547–2549) and `wireCoreEvents()`'s `on()` wrapper (2197–2216) both close over a `wiredRunId` captured at wiring time and bail if `R.identity.runId` has since changed — this stops a stale run's late-arriving async callback from writing into a new run's report. `pollStats()` goes further: it re-checks `R.identity.runId`, `browserRec.runId`, *and* `browserRec.pcId` (1399–1400) before writing a resolved `getStats()` promise's data, because a `getStats()` call can resolve after `stopPlayer()`/`resetRun()` has already run. This is good defensive design, worth keeping as-is in any future revision.

**3.4 — The 15 p2p-media-loader-hlsjs events this harness listens for**, all bound through the same `on()` wrapper (2218–2466): `onStreamAdded`, `onStreamRegistrationError`, `onPeerConnect`, `onPeerClose`, `onPeerError`, `onPeerWarning`, `onPeerConnectError`, `onTrackerError`, `onTrackerWarning`, `onSegmentStart`, `onSegmentAbort`, `onSegmentError`, `onChunkDownloaded`, `onChunkUploaded`, `onSegmentLoaded`. Confirms there is still no `onTrackerConnected`-equivalent event in the library's `CoreEventMap` — see §5.6.

**3.5 — Path A (event-capture): live but empirically empty.** The capture IIFE's own `pc.addEventListener("icecandidate", ...)` (lines 310–319) pushes every locally-gathered candidate into `r.ice.candidates`. `syncV11BrowserProtocol()` (2970–2991) later reads exactly this array (`p.ice.candidates`, where `p = pc.__hsV11`) to build `R.webrtc.peerConnections[].localCandidates`/`.candidateTypes`. This is the code path HIV-000 found producing zero local candidates across all 33 runs, including the one with 101MB/76MB of real transfer. The wiring itself is correct by inspection (§4 below has no bug here) — see §5.1 for what that does and doesn't tell us.

**3.6 — Path B (`getStats()` polling): the one that actually works.** `pollStats()` (1380–1587), called every 1.5s (`setInterval(pollStats, 1500)`, line 3465), iterates `window.__HS_V11_PEER_CONNECTIONS`, calls `pc.getStats()` on each, and pulls `candidate-pair`/`transport`/`remote-candidate` stats directly from the report — this is what produced the `succeeded` ICE pair and the real byte counts in HIV-000's one successful run.

## 4. Confirmed bugs (SOURCE PROVEN — verified against the file directly)

### 4.1 `correlatePeerIdToBrowserPc()` reads and writes the wrong object — it is a permanent no-op

Lines 3129–3165. Called from `onPeerConnect`/`onPeerConnectError` (2291, 2308) with a remote `peerId` string, its job is to attribute that peer ID to whichever open `RTCPeerConnection` it most likely belongs to. But it filters `window.__HS_V11_PEER_CONNECTIONS` like this:

```
var open = all.filter(function(p){ return p && p.runId === runId && !p.closed; });
```

`all` is an array of raw `pc` objects (per §3.1). `p.runId` and `p.closed` are **not properties of `pc`** — they live on `pc.__hsV11.runId` / `pc.__hsV11.closed`. Every other function that reads this same array (`pollStats()` at 1387–1389, `syncV11BrowserProtocol()` at 2962–2964) correctly dereferences `.__hsV11` first. This one function doesn't. The result: `p.runId` is always `undefined`, `undefined === "<the actual run's uuid>"` is always `false`, so `open` is always `[]`, `pool` is always `[]`, `pool[0]` is always `undefined`, and the `if(pool[0]){...}` block (3153–3164) that would actually write `peerId`/`remotePeerId`/`peerCorrelationConfidence` onto the record **never executes, on any call, in any run.**

**Consequence:** `R.webrtc.peerConnections[].peerId` is unconditionally `null` in every exported JSON this harness has ever produced with this function's help — `syncV11BrowserProtocol()` reads `p.peerId || p.remotePeerId || null` (line 2982) and both are always null. This directly explains a gap in HIV-000: the "who was the peer, actually?" section had to reconstruct peer↔connection attribution by hand (cross-referencing timing windows and remote IP addresses across separate JSON fields) instead of reading it straight off a `peerId` field on the connection record, because that field has never once been populated.

**Fix:** change the three `p.___` reads to `p.__hsV11.___` (or filter on `p.__hsV11` directly, matching the pattern already used in `pollStats`/`syncV11BrowserProtocol`).

### 4.2 `attachPC()` / `attachDataChannel()` are dead code — never called

Lines 1228–1352 define a *second*, independent WebRTC event-listener/state-tracking implementation (`attachPC(pc, index)`, which internally calls `attachDataChannel(rec, channel)`). `grep -n "attachPC("` against the full file returns exactly one hit — its own definition. There is no call site anywhere. `attachDataChannel` is likewise only reachable from inside `attachPC`, so it's unreachable too. Neither function contributes anything to the exported report; `R.webrtc.peerConnections` is populated exclusively through the Path-A/Path-B mechanism in §3.5/3.6, not through this block.

This isn't just inert — it's a plausible source of confusion for whoever next edits this file, since `attachPC`'s state-tracking (via `recordState()`, `addCandidateRecord()`) looks like it *should* be the thing wiring up `R.webrtc.peerConnections`, and it would be easy to assume it's live and debug in the wrong place. Recommend either deleting it or wiring it in (it has no functional advantage over the currently-live path, so deletion is simpler).

### 4.3 `resetRun()`'s rebuilt `R` silently drops the `swarm.coreGetStreams` field present in the initial literal

Comparing every object key in the 876–1074 literal against every object key in the 2782–2948 rebuild (programmatic diff, not eyeballed): the two blocks match on all 149 other keys; `coreGetStreams` exists only in the initial literal's `swarm` object (line 998), not in `resetRun()`'s (2886–2891). Concretely: after any `Start/Restart` click beyond the very first one, `R.swarm.coreGetStreams` is `undefined` until the first `pollStats()` tick sets it (line 1413) rather than `null` from the start. Harmless in this specific case (nothing reads it before the first poll fires ~1.5s in), but it's a live demonstration of the exact risk described in §3.2 — this field *will* eventually be one that matters, on some future edit, and nothing will flag the mismatch.

**Fix suggestion:** factor both blocks into one `makeFreshR()` function that both the initial declaration and `resetRun()` call, so the two can't drift again by construction.

## 5. What this review adds to HIV-000's findings

### 5.1 The empty-candidates mystery (Path A) — traced to exact code, root cause still open

HIV-000 observed 0 local candidates recorded across 87 wrapped RTCPeerConnections in the one successful run, including the connection that carried 101MB/76MB of real traffic, and hypothesized this was "probably reading only the broken event-capture path." This review confirms *which* path (§3.5) and confirms it is **not** broken in the sense of §4.1/§4.2 — the interception mechanism (§3.1) is sound, the listener registration happens synchronously before the wrapped `pc` is ever handed back to the caller, and `syncV11BrowserProtocol()` reads the right property off the right object. That means the wrapped connections genuinely exist (their count — 87 — comes from this same mechanism working), yet the native `icecandidate` DOM event apparently never fires with a non-null candidate on any of them, even on the one connection `getStats()` independently confirms reached a `succeeded` candidate pair. STRONG INFERENCE: this is either a genuine browser/library-interaction quirk specific to how p2p-media-loader-hlsjs's bundled WebRTC usage gathers candidates, or something not visible from static reading at all. **UNPROVEN-OPEN** — recommend a one-line temporary `console.log` inside the line-310 `icecandidate` listener for one live run, to settle directly whether the event ever fires with `e.candidate !== null` on these connections. That single check would resolve this faster than further code reading.

### 5.2 The level-lock/relock code is sound on its own terms — the drift is downstream of it

`attachHlsEvents()`'s `MANIFEST_LOADED` handler sets `hlsInstance.currentLevel = found.index` once the CONTROLLED rendition is matched (2582–2586), and its `LEVEL_SWITCHED` handler re-forces `hlsInstance.currentLevel = R.selectedVariant.levelIndex` (2621–2625) any time `d.level` (hls.js's own self-reported active level) disagrees with the locked target. In the successful run, `LEVEL_SWITCHED` never disagreed — `activeLevelIndex` stayed 3 the whole time, so the relock branch correctly never fired (an empty `playerRecovery.levelDriftCorrections`, exactly as HIV-000 reported, is the *correct* behavior of this code given what hls.js told it). Separately, `onSegmentLoaded` (2421–2466) does its own **per-segment** check — `seg.infoHash === R.swarm.controlledInfoHash` (2452–2455) — and that correctly stayed false for every segment all run. So neither piece of this file's own logic is misreporting anything; both are behaving exactly as designed. The actual disagreement is between what hls.js's `LEVEL_SWITCHED` event claims (`level: 3`) and what rendition its own fragment loader is truly requesting — that gap lives inside hls.js 1.7.0 / p2p-media-loader-hlsjs 4.0.0 internals, not in this file. HIV-000's own open question #2 ("does p2p-media-loader's own stream selection override hls.js's currentLevel?") is the right next question; this review doesn't resolve it, but it does rule out "the diagnostic's lock logic is buggy" as an explanation.

One plausible mechanism worth naming (STRONG INFERENCE, not verified): p2p-media-loader-hlsjs likely registers a P2P `stream` (triggering `onStreamAdded`) for every rendition in the manifest up front, for swarm-discovery purposes, independent of which rendition is actually being played — that would explain why `R.swarm.controlledInfoHash` got populated at all (from `onStreamAdded` firing once for level 3) even though every segment fetch happened against level 0's stream instead. If true, the fix belongs in how p2p-media-loader-hlsjs's stream-selection interacts with hls.js's `currentLevel`, not in this diagnostic file.

### 5.3–5.5 Three confirmations that earlier fixes are still in place / gaps still open

- **5.3 — Confirmed:** `STREAM_TRANSPORT.p2ponly` (663–674) sets `simultaneousHttpDownloads: 0` — the actual "P2P-only" lever identified in the earlier v7 research (see `[[hivestream-cytube-integration]]`), not the milder v9.1 approximation. v12.4.1's P2P-only mode is wired correctly against that earlier finding.
- **5.4 — Confirmed:** the Custom-swarm-mode empty-string guard from the v6 fix (`if (!v) { alert(...); return null; }`, 2519–2522) is still present — the original v5 bug (blank field silently sending `swarmId: ''`) cannot recur here.
- **5.5 — Still open:** no TURN server configuration exists anywhere in this file — `buildP2PConfig()` (2510–2541) never sets an `rtcConfig`/`iceServers` key, and `WEBRTC_CONNECTION_BUDGET_LIBRARY_DEFAULTS` (678–687) is explicitly documentation-only (its own `note` field says so; nothing in `buildP2PConfig()` reads it). The v7 research's proposed TURN toggle was never built into any version through v12.4.1. This matches HIV-000's own finding that the successful run's connection came from a public relay-hosted stranger rather than a locally-negotiated peer, and its open item #1 (re-run with a custom swarmId) doesn't by itself address the STUN-only NAT-traversal question.

### 5.6 Tracker-health ambiguity is a known, carried-forward limitation, not a regression

`notePeer()` (1683–1746) still infers a tracker's liveness from peer-sighting events carrying that tracker's URL (`trec.status = "peer-seen"`, 1731–1732) — the same workaround introduced in v6 for the library's missing "tracker connected" event (confirmed absent again here: none of the 15 bound events in §3.4 is a connection-status event). A tracker that's silently healthy but has found no peers yet is still indistinguishable from one that never connected — this is a library-level gap (`CoreEventMap` has no such event), not something fixable in this file. HIV-000's open item #4 ("investigate why only 1 of 3 configured trackers ever returns peers") remains genuinely open; this review just confirms the diagnostic isn't hiding the answer.
