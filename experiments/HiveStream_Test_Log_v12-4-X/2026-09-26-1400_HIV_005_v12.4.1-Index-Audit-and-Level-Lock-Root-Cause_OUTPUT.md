## 2. Level-lock root cause: RESOLVED (SOURCE PROVEN)

### 2.1 Recap of the open question

From the WS-082/HIV-000 breakthrough run: `hlsInstance.currentLevel` was set to 3 (the index the diagnostic computed for the controlled 848×480 rendition) in the `MANIFEST_LOADED` handler. `LEVEL_SWITCHED` consistently reported `level: 3` for the full 15-minute run, with `playerRecovery.levelDriftCorrections` empty (the diagnostic's own re-lock watchdog never fired). Yet **100% of actual segment fetch URLs** — HTTP and P2P alike — came from the 1280×720 "hd" rendition (infoHash `Dd+yrwrnofWI3vWhfz1l`), never the intended 480p rendition (infoHash `i0q7IwL7towfhu4Xnofx`). HIV-001 confirmed this isn't a bug in the diagnostic's own lock/re-lock code and correctly flagged it as needing library-internals investigation or live runtime logging — it did not attempt the library-source read itself.

### 2.2 Method

Pulled real, exact-version source (not the CDN's minified dist, and not assumptions from memory) via npm:

```
npm pack hls.js@1.7.0 p2p-media-loader-hlsjs@4.0.0 p2p-media-loader-core@4.0.0
```

These match the exact pinned versions v12.x already uses (confirmed against the v12 conformance pass in `technical-findings.md`: hls.js@1.7.0 dist confirmed, p2p-media-loader-hlsjs@4.0.0 confirmed as npm's `latest` dist-tag).

### 2.3 Step 1 — ruled out the P2P layer entirely (SOURCE PROVEN)

`p2p-media-loader-hlsjs/src/fragment-loader.ts`'s `FragmentLoaderBase.load()` takes `context.url` as given and passes it straight through to the P2P engine / HTTP fallback. It has no branch, no lookup, no override that chooses *which* level's URL gets requested — it only decides *how* an already-chosen URL gets fetched (P2P vs HTTP). Likewise `engine.ts`'s hls.js integration (`bindHls`, `updateLoaders`) never touches `hls.currentLevel`, `hls.nextLoadLevel`, or the level controller in any way.

**This rules out the p2p-media-loader-hlsjs layer as the mechanism.** Whatever picks level 0's URL instead of level 3's, it happens entirely inside hls.js itself, before the fragment loader is ever invoked.

### 2.4 Step 2 — ruled out the ABR emergency-downswitch path (SOURCE PROVEN)

hls.js has a background safety mechanism (`abr-controller.ts`, `_abandonRulesCheck`, polled every 100ms) that can abort a slow-loading fragment and force a downswitch via `hls.nextLoadLevel = hls.nextAutoLevel = <lowerLevel>`. This looked like a promising candidate (mixed HTTP/P2P transport could plausibly look "slow" to this heuristic), and tracing `level-controller.ts`'s `nextLoadLevel` **setter** shows it applies `this.level = nextLevel` **unconditionally** — i.e. this specific write path does *not* check `manualLevelIndex` before mutating `currentLevelIndex`, unlike the `nextLoadLevel` *getter*, which does respect manual mode. That asymmetry is real and worth flagging as a general hls.js caveat (§2.6). But `_abandonRulesCheck` itself bails out immediately if `!this.hls.autoLevelEnabled` (`abr-controller.ts` line ~277), and `autoLevelEnabled` (`hls.ts`) is defined as `this.levelController.manualLevel === -1` — false whenever a manual lock is active. **This path is correctly gated and was not the cause here.**

### 2.5 Step 3 — the actual root cause: two different arrays, two different index spaces (SOURCE PROVEN)

This is the finding. Two separate arrays exist inside hls.js, both nominally "the levels," indexed differently:

1. **`data.levels`** — the array attached to the `Events.MANIFEST_LOADED` event payload. Traced to its origin in `hls.js/src/loader/playlist-loader.ts`: this is the raw, parser-order list of variants exactly as declared in the master `.m3u8`, in manifest-declared order. This array is never sorted or mutated after this point — `data.levels` keeps whatever order the manifest author used.
2. **`this._levels`** (internal to `level-controller.ts`) — built separately inside `LevelController.onManifestLoaded()`, which is `level-controller`'s *own* internal `MANIFEST_LOADED` handler (registered before any application code can attach a listener, since `level-controller` is constructed inside hls.js's own base constructor). This handler reads from `data.levels` too, but builds a **new** local array via `filterAndSortMediaOptions()`, which explicitly does:

   ```ts
   levels.sort((a, b) => {
     // ...tie-break chain, but the primary key is:
     return a.height - b.height;
     // (then bitrate, frame rate, etc. as tie-breaks)
   });
   ```

   This sorted array — **not** `data.levels` — becomes `this._levels`, and `this._levels` is what `hls.currentLevel = N` / `hls.manualLevel` / `hls.nextLoadLevel` all index into (`level-controller.ts`, `set level(newLevel)`: `this._levels[newLevel]`).

The diagnostic's `attachHlsEvents()` computes its "controlled rendition is index 3" by scanning `d.levels` inside its own `MANIFEST_LOADED` handler — i.e. it reads the **unsorted, manifest-declared-order** array — then calls `hlsInstance.currentLevel = found.index (3)`, which indexes into the **sorted-by-height** internal array instead.

Per the already-recorded manifest structure for the Mux fixture (from the v10 milestone doc, confirmed again here): declared order is **720p, 320×184, 512×288, 848×480, 1080p**. Sorted ascending by height, the order becomes **320×184, 512×288, 848×480, 720p, 1080p**. Walking both arrays:

| index | `data.levels` (unsorted, what the diagnostic scans) | `this._levels` (sorted, what `currentLevel=N` actually selects) |
|---|---|---|
| 0 | 720p | 320×184 |
| 1 | 320×184 | 512×288 |
| 2 | 512×288 | **848×480** |
| 3 | **848×480** | **720p** |
| 4 | 1080p | 1080p |

The diagnostic finds 848×480 at index 3 in the array it scanned, and locks `currentLevel = 3` — which, in the array hls.js actually uses, is **720p**. This is exactly the rendition that was observed being fetched 100% of the time (infoHash `Dd+yrwrnofWI3vWhfz1l`, the "hd" naming). It also fully explains why there was never any detected "drift": `LEVEL_SWITCHED` consistently reported `level: 3` because hls.js never stopped playing its own internal index 3 — there was no runtime drift at all. The mismatch is a one-time index-space collision made once, at lock time, between two arrays that happen to share a length and a type shape but not an order.

**Verdict:** RESOLVED. This is the direct, complete explanation for the WS-082 finding, with no remaining unexplained gap. Confidence: SOURCE PROVEN for the mechanism (both arrays' construction and sort behavior read directly from hls.js 1.7.0 source); STRONG INFERENCE (not yet re-run) that this fully accounts for the specific 720p-instead-of-480p swap observed in the WS-082 run, since it depends on the Mux fixture's specific declared manifest order, which was recorded in a prior session's notes rather than re-parsed from the live manifest in this session.

### 2.6 The fix

Do not compute the controlled-rendition index from `d.levels` (the `MANIFEST_LOADED` event payload) at all. Two options, in order of robustness:

1. **Match by identity, not index.** After setting up level matching, look up the rendition by width/height/bitrate directly against `hlsInstance.levels` (the *live*, already-sorted getter — `hls.levels`, not the event payload) and use **that** array's index for `hlsInstance.currentLevel =`. Since both the matching and the assignment would then operate on the same (sorted) array, the index spaces can't disagree.
2. Alternatively, keep matching against `d.levels` for the resolution/bitrate values (fine, since those are the same underlying data either way — sort doesn't change field values, only order), but re-resolve the matched level's index by searching `hlsInstance.levels` for the level object with the same width/height/bitrate immediately before calling `currentLevel =`, rather than trusting the index found during the `d.levels` scan.

Either fix is a small, targeted change confined to the "find and lock the controlled rendition" block in `attachHlsEvents()` (the `MANIFEST_LOADED` handler around the CONTROLLED_VARIANT matching logic HIV-001 already reviewed in §5.2). This does **not** touch p2p-media-loader-hlsjs at all — it's a pure hls.js API-usage fix in the diagnostic.

Also worth flagging as a secondary hls.js API caveat surfaced along the way (§2.4): `nextLoadLevel`'s setter bypasses the manual-lock guard that its own getter enforces. This didn't cause the WS-082 symptom (the abandon-rules path that would trigger it is correctly gated), but it means a manual lock is not fully "safe" against every internal hls.js write path in 1.7.0 — worth a comment in the code, not worth an immediate fix.

### 2.7 Recommended verification

Re-run the v12.4.1 (or a v12.5 with the fix from §2.6) diagnostic and confirm the fetched segment infoHash now matches the intended 480p rendition. This should be a fast, cheap confirmation — no new instrumentation needed, since the existing verdict/segment-infoHash reporting already surfaces exactly the field needed to check it.

## 3. Custom swarmId / swarm-scoping feasibility (SOURCE PROVEN — confirms HIV-001 §5.4, adds the tracker-exposure nuance)

Confirmed directly in `index.html` (~lines 2505–2545): the diagnostic's swarm-mode toggle is real and functional, not a stub.

- **Natural mode:** `core.swarmId` is never set — p2p-media-loader-core falls back to its own default, which is derived from the manifest URL (content-scoped, matching the earlier-documented default behavior).
- **Custom mode:** the diagnostic reads a user-supplied string and does `core.swarmId = v` directly before the engine is bound.

This is a real guard, and a custom-swarmId re-test is fully feasible with the harness as it stands today — no code changes needed to run it.

**One nuance worth being explicit about for the re-test's interpretation:** setting a custom `swarmId` does **not** switch away from the public trackers. `TRACKER_HINTS` (the tracker URL list: `tracker.novage.com.ua`, `tracker.webtorrent.dev`, `tracker.openwebtorrent.com`) is applied unconditionally, regardless of swarm mode. What changes is the **content identity** used for peer matching: per the already-established stream-identity formula (`streamSwarmId = ${peerProtocolVersion}-${swarmId}-${type}-${identityHash}`, `infoHash` derived from that), a custom swarmId produces a different `infoHash` than natural mode would for the same manifest. A stranger on the same public tracker who doesn't already know your specific custom swarmId string has no way to derive or guess your `infoHash` and therefore cannot discover or join your swarm — the tracker only pairs peers announcing the *same* infoHash. So: **feasible, and should work as intended** for excluding public-swarm contamination (i.e. the Mullvad-VPN-peer scenario from WS-082 specifically), even though the transport (which trackers get contacted) is unchanged. This is a meaningful distinction from "self-hosting a private tracker" (the WS-083 recommendation) — a custom swarmId is a cheap, already-implemented way to get *content-level* privacy from strangers on public trackers; a self-hosted tracker is a separate, complementary way to avoid *metadata* exposure (IP addresses, connection timing) to the public tracker operators themselves. Both remain worth doing; they solve different exposure vectors.

**Recommendation:** run the custom-swarmId re-test next, combined with the level-lock fix from §2.6 in the same revision, since both are small, already-scoped changes and testing them together saves a round trip.
