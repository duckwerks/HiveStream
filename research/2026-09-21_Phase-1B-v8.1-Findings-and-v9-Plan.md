## 1. Executive finding

The v8.1 experiment established that the HiveStream browser diagnostic is capable of observing and proving real P2P media transfer through p2p-media-loader/WebRTC.

The strongest evidence is not simply the aggregate P2P byte counter. The diagnostic recorded actual p2p-media-loader peer IDs and attributed HLS media segments to those peer IDs. The four-browser run therefore lets us reconstruct actual media-transfer relationships.

This is a major instrumentation milestone.

It does **not** yet prove successful P2P media transfer between the phone and laptop over separate Internet connections. Cross-device peers were discovered by the tracker, but the observed cross-device attempts ended in connection errors and did not supply media segments.

The correct next step is therefore not to redesign the architecture or force a particular known-peer connection. The next experiment should test natural participation in a P2P swarm while preserving the instrumentation that tells us exactly which peer supplied which media.

## 2. v8.1 four-browser run

The important run contained four simultaneous browser sessions:

- Phone Chrome
- Phone Firefox
- Laptop Chrome
- Laptop Firefox

### Actual p2p-media-loader peer IDs

| Physical device | Browser | Actual peer ID |
|---|---|---|
| Phone | Firefox | -PM0400-xMt0lQbZHy8D |
| Phone | Chrome | -PM0400-bT6x8pyoKX8s |
| Laptop | Firefox | -PM0400-Wvl6jIQhN10V |
| Laptop | Chrome | -PM0400-J9NppyV0Rye8 |

These are observed p2p-media-loader identities, not HiveStream-generated replacement IDs.

### Verified media edges

**Phone Firefox ↔ Phone Chrome**

Phone Chrome received approximately 80.6 MB of P2P media and recorded more than 24 P2P segments explicitly sourced from -PM0400-xMt0lQbZHy8D, the Phone Firefox peer.

Phone Firefox recorded approximately 81.6 MB uploaded and approximately 7.85 MB downloaded, with P2P media segments attributed to -PM0400-bT6x8pyoKX8s, the Phone Chrome peer.

This is reciprocal peer-level evidence.

**Laptop Firefox ↔ Laptop Chrome**

Laptop Chrome received 31,467,021 bytes from -PM0400-Wvl6jIQhN10V, the Laptop Firefox peer.

Laptop Firefox recorded 31,467,021 bytes uploaded and received 9,627,668 bytes from -PM0400-J9NppyV0Rye8, the Laptop Chrome peer.

Laptop Chrome recorded approximately 9,627,668 bytes uploaded.

Again, the peer IDs and byte directions line up.

### Cross-device attempts

Cross-device peers were also discovered.

- Laptop Firefox discovered Phone Chrome -PM0400-bT6x8pyoKX8s; the later event was connect-error.
- Phone Chrome discovered Laptop Firefox -PM0400-Wvl6jIQhN10V; the later event was connect-error.

No P2P media segments were attributed to those cross-device peers.

Therefore:

- Tracker discovery across devices: observed.
- Cross-device WebRTC/media transfer: not established by this run.

## 3. What v8.1 proves

### Proven

1. p2p-media-loader 4.0.0 initializes successfully.
2. The WebTorrent-compatible tracker discovers peers.
3. The actual p2p-media-loader peer identity can be observed.
4. WebRTC/P2P connections can succeed.
5. P2P media chunks can be received.
6. HLS segments can be attributed to a specific remote peer.
7. P2P upload/download accounting can be correlated between the two sides.
8. Two browsers on the same physical device can exchange real media P2P.
9. The second physical device can likewise have two browsers exchange real media P2P.
10. The instrumentation distinguishes peer discovery, connection, and actual media transfer.

### Not yet proven

1. P2P media transfer between the phone and laptop across their separate Internet connections.
2. Successful NAT traversal between those two networks.
3. Successful P2P exchange with an unknown public-swarm peer.
4. That the current public tracker is the limiting factor in cross-device connectivity.
5. That a HiveStream-controlled custom swarm ID behaves correctly across separate networks.
6. That the diagnostic's current swarm-identity display exposes the authoritative p2p-media-loader identity fields.

## 4. Swarm identity finding

The v8.1 report sometimes contains:

    resolvedSwarmId: null
    controlledInfoHash: null

while actual tracker and transfer events contain real infohashes such as:

- Dd+yrwrnofWI3vWhfz1l
- i0q7IwL7towfhu4Xnofx

This should **not** currently be interpreted as proof that p2p-media-loader generated a null or invalid swarm identity.

p2p-media-loader v4 moved stream-identity derivation into the core. A registered stream has authoritative fields including runtimeId, swarmId, streamSwarmId, identityHash, and infoHash. The v4 API also provides Core.getStreams() and onStreamAdded for inspecting computed identity, and onStreamRegistrationError for registration failures.

Therefore the next diagnostic should read the core's authoritative stream identity instead of trying to reconstruct it from tracker events.

Reference: p2p-media-loader v4 Migration Guide:
https://github.com/Novage/p2p-media-loader/blob/main/MIGRATION.md

## 5. Testing principle for the next phase

The first P2P test should **not** require two predetermined known peers.

Known peer identity is an observation tool, not the networking objective.

### Stage A — Natural public swarm

One HiveStream browser joins a compatible public swarm and is allowed to discover whatever compatible peers are available.

Question:

> Can this browser obtain actual HLS media segments through P2P/WebRTC from any compatible peer?

Unknown peers are valid and important evidence.

### Stage B — Peer attribution

For every peer, record:

- local peer ID
- remote peer ID
- known/unknown status
- device/browser label if it is one of our controlled browsers
- tracker URL through which the peer was discovered
- infohash
- connection event
- connection error/close
- P2P chunks received
- P2P bytes received
- P2P bytes uploaded
- first-seen and last-seen times

### Stage C — Controlled two-device test

After natural swarm P2P is working, run one browser on the laptop and one browser on the phone, with the phone on cellular data and Wi-Fi disabled.

This isolates the cross-network question without making predetermined peer identity a prerequisite for the first P2P proof.

### Stage D — Controlled HiveStream swarm identity

Only after the basic P2P path is established should we deliberately set the same HiveStream swarm ID on two controlled browsers and verify that the resulting stream identity and infohash are identical.

This separates P2P/WebRTC connectivity from HiveStream swarm-identity design.

## 6. WSS tracker strategy for v9

p2p-media-loader supports multiple WebTorrent-compatible trackers. Its documentation also warns that public trackers have limited capacity and should not be treated as production infrastructure.

For v9, adding a **second public WSS tracker** is useful because it increases the opportunity for peer discovery and lets us determine whether a failure is tracker-specific.

However, adding many trackers at once would make the experiment harder to interpret.

### Recommendation

Use two WSS trackers:

1. wss://tracker.openwebtorrent.com
2. wss://tracker.btorrent.xyz

Record the tracker URL on every peer event.

The purpose of tracker #2 is not to fix the current system. Tracker discovery already works. Its purpose is to increase natural peer-discovery opportunities and provide another observable variable.

Reference: p2p-media-loader FAQ:
https://github.com/Novage/p2p-media-loader/blob/main/FAQ.md

## 7. v9 should focus on P2P, not eliminate HTTP

HTTP must remain enabled.

p2p-media-loader is deliberately a P2P-assisted delivery system: HTTP supplies segments when peers do not have them, while P2P supplies segments when peers do. The diagnostic should emphasize P2P in its reporting rather than disabling the fallback.

The primary proof hierarchy should be:

    tracker discovery
          ↓
    remote peer identified
          ↓
    WebRTC connection attempted
          ↓
    WebRTC connection succeeds
          ↓
    P2P chunk received
          ↓
    chunk attributed to remote peer
          ↓
    HLS segment attributed to remote peer
          ↓
    P2P media proof

HTTP activity remains recorded as a control/reference measurement.

p2p-media-loader documents that a stream generally needs to be obtained from HTTP at least once before a peer can share those segments. Therefore removing HTTP would make this a worse test of the library's normal delivery model, not a stronger one.

## 8. v9 instrumentation changes

The v8.1 instrumentation should remain the foundation. v9 should add precision rather than a new architecture.

### A. Read authoritative stream identity

Expose:

- runtimeId
- swarmId
- streamSwarmId
- identityHash
- infoHash

from the p2p-media-loader core where available.

Also capture:

- onStreamAdded
- onStreamRegistrationError

This should resolve the current ambiguity around resolvedSwarmId.

### B. Make peer records first-class

Each remote peer should have a persistent record containing:

- peer ID
- known/unknown status
- known device/browser label when applicable
- tracker URLs
- infohashes
- connection events
- connection errors and closes
- P2P bytes down/up
- P2P segment count
- first-seen/last-seen timestamps

### C. Keep a known-peer registry

Only explicitly identified test browsers should be marked known.

Every other peer should automatically remain:

    known: false
    knownAs: null

This lets the swarm remain natural while still allowing forensic identification afterward.

### D. Record peer-to-segment edges

Record which peer supplied each P2P segment.

Example:

    segment 42 ← Peer A
    segment 43 ← Peer A
    segment 44 ← Peer B
    segment 45 ← Peer A

This allows the exported report to reconstruct the actual P2P media graph.

### E. Record tracker-to-peer relationships

With two trackers, record:

    tracker A
      ├── Peer 1
      └── Peer 2

    tracker B
      ├── Peer 2
      └── Peer 3

This tells us whether the second tracker actually adds discovery diversity.

### F. Preserve existing WebRTC evidence

Do not remove the current ICE candidate types, candidate pairs, UDP/TCP information, relay detection, connection state history, data-channel state, or WebRTC peer-connection records.

These remain important when a peer is discovered but fails to connect.

## 9. What v9 should not do

Do not:

- add TURN merely because cross-device P2P has not yet been proven;
- redesign the transport layer;
- replace p2p-media-loader;
- create a second HiveStream peer-ID system;
- require a known peer for the basic test;
- require a custom swarm ID for the basic P2P test;
- remove HTTP fallback;
- add a large collection of trackers;
- interpret connect-error as proof that a tracker is broken;
- interpret a null diagnostic field as proof that the underlying library identity is null.

The v8.1 evidence is strong enough that the next step should be a better experiment, not a new architecture.

## 10. Proposed v9 experiment

### Configuration

- p2p-media-loader 4.0.0
- HLS.js 1.7.0
- natural swarm mode
- controlled 848×480 / 836280 rendition
- HTTP fallback enabled
- two WSS trackers
- no TURN
- normal browser ICE behavior
- complete peer attribution

### Primary objective

> **Demonstrate P2P HLS segment exchange with any compatible peer in the swarm, including unknown peers, and identify the exact peer responsible for each P2P transfer.**

### Secondary objectives

1. Determine whether the second tracker increases peer discovery.
2. Determine whether unknown public peers can supply media.
3. Determine whether cross-device peers can establish WebRTC.
4. Determine whether cross-device peers can supply actual HLS segments.

## 11. Current conclusion

v8.1 should be considered a successful instrumentation milestone and a **partial P2P proof**.

The most important discovery is that we no longer have to infer P2P behavior from aggregate counters. We can identify the actual p2p-media-loader peer and attribute actual media segments to that peer.

The next experiment should exploit that capability.

The immediate target is:

**natural swarm → any peer → WebRTC → actual P2P HLS segment → exact peer attribution.**

After that:

**known cross-device peer → separate networks → P2P media.**

After that:

**controlled HiveStream swarm identity → verified identical computed stream identity/infohash → controlled P2P exchange.**

This keeps the experimental order clean and prevents a failure in one layer from being mistaken for a failure in another.

### Source notes

The p2p-media-loader FAQ states that WebTorrent-compatible trackers provide WebRTC signaling, that multiple trackers can be configured, that peers sharing a stream need the same swarm ID, and that HTTP fallback is part of the P2P-assisted delivery model. The v4 migration guide documents the authoritative stream identity fields and Core.getStreams()/onStreamAdded/onStreamRegistrationError APIs.
